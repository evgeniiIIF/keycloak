# Анализ утверждения о CSRF-токене

## Вердикт: Утверждение ПОЧТИ ВЕРНО, но с неточностями

### Что верно

1. **CsrfMiddleware записывает csrfToken в сессию только при отсутствии куки** — подтверждено кодом (`csrf.middleware.ts:9`): `if (!req.cookies['XSRF-TOKEN'])` — весь блок генерации и записи в сессию обёрнут этим условием.

2. **Если кука уже существует, сессионный csrfToken не обновляется** — верно. При наличии куки middleware просто вызывает `next()` (`csrf.middleware.ts:26`), не обращаясь к сессии.

3. **При `session.csrfToken === undefined` вторая проверка пропускается** — подтверждено (`security.middleware.ts:80`):
   ```ts
   if (session?.csrfToken && session.csrfToken !== cookie) {
   ```
   Оператор `&&` означает: если `csrfToken` отсутствует — вся проверка пропускается, остаётся только Stage 1 (cookie === header).

### Где утверждение неточно

**Сценарий «очистки кук логином из другого браузера»** описан некорректно. Каждый браузер хранит собственный `connect.sid` и `XSRF-TOKEN` — они не конфликтуют. Логин из другого браузера не влияет на куки первого.

**Реальный критический сценарий** — другой:

1. Сессия уничтожена на сервере (Redis TTL, ручное удаление, `session.destroy()`)
2. Браузер всё ещё хранит `XSRF-TOKEN` куку (она не была清除лена)
3. Пользователь делает запрос → CsrfMiddleware видит куку → **ничего не делает** → `next()`
4. Новая сессия создаётся без `csrfToken` (undefined)
5. SecurityMiddleware: Stage 1 проходит (cookie === header), **Stage 2 пропущена** (csrfToken undefined)
6. **CSRF-защита ослаблена до простого double-submit cookie**

### Уязвимость

Да, это реальная проблема. Без сессионного токена защита полагается только на:
- `SameSite=strict` куки (но это не защищает от поддоменных атак)
- Невозможность чтения куки с другого origin (но `httpOnly: false` — кука доступна JS)

Если атакующий может заставить браузер жертвы отправить запрос с кукой и заголовком (XSS на поддомене, мутированные запросы), Stage 1 пройдёт.

### Рекомендация

**Согласен с рекомендацией**: привязывать CSRF-токен к сессии всегда, а не только при первой установке куки.

## План исправления

### Изменение в `csrf.middleware.ts`

**Цель**: ВСЕГДА записывать `csrfToken` в сессию, даже если кука уже существует.

```ts
// БЫЛО:
use(req: Request, res: Response, next: NextFunction): void {
  if (!req.cookies['XSRF-TOKEN']) {
    const token = crypto.randomBytes(32).toString('hex');
    // ... установка куки ...
    if (req.session) {
      req.session.csrfToken = token;
      req.session.save(() => next());
      return;
    }
  }
  next();
}

// СТАЛО:
use(req: Request, res: Response, next: NextFunction): void {
  const existingCookie = req.cookies['XSRF-TOKEN'];

  if (!existingCookie) {
    const token = crypto.randomBytes(32).toString('hex');
    const isProd = config.nodeEnv === 'production';
    res.cookie('XSRF-TOKEN', token, {
      httpOnly: false,
      secure: isProd,
      sameSite: 'strict',
      path: '/',
    });
  }

  // Всегда привязываем токен к сессии
  if (req.session) {
    req.session.csrfToken = existingCookie || req.cookies['XSRF-TOKEN'] || crypto.randomBytes(32).toString('hex');
    req.session.save(() => next());
    return;
  }
  next();
}
```
