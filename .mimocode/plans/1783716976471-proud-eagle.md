# Анализ и исправление логики рефреш токена

## Архитектура (текущая и правильная)

```
Frontend → BFF (прокси) → Downstream (protected-service)
                              ↓
                         401 если токен истёк
                              ↓
                    BFF HTTP client рефрешит + повторяет
```

- BFF — прокси, не валидирует срок жизни токенов
- Downstream сам проверяет JWT и возвращает 401
- BFF HTTP client (`http-client.ts`) ловит 401, рефрешит, повторяет запрос
- Security middleware проверяет только: сессия существует, CSRF, роли

## Найденные проблемы

### P0: Security middleware блокирует запросы с истекающим токеном

**Файл**: `bff/src/middleware/security.middleware.ts:55-68`

Middleware проверяет `payload.exp < now + 30` и возвращает 401 "Token expired — refresh first". Это неправильно — downstream должен сам решать, валиден ли токен. Middleware блокирует запрос раньше, чем он дойдёт до downstream, и HTTP client не может обработать 401.

Результат: пользователь разлогинивается за 30 сек до реального истечения токена, хотя refresh token ещё валиден.

**Решение**: Убрать `skipExpiryCheck` и всю логику expiry check из middleware. Middleware должен проверять только:
1. Сессия существует (есть `accessToken`)
2. CSRF валиден
3. Роли sufficient

### P1: `POST /api/auth/refresh` не имеет lock'а от параллельных вызовов

**Файл**: `bff/src/controllers/auth.controller.ts:73-81`

HTTP client имеет `token-refresh-lock.ts` для дедупликации. Контроллер — нет. Параллельные вызовы могут сломаться при refresh token rotation.

**Решение**: Добавить lock из `token-refresh-lock.ts` в `AuthController.refresh()`.

### P1: Сессия не сохраняется в Redis сразу после рефреша

**Файл**: `bff/src/services/auth.service.ts:61-78`

`refreshTokens()` обновляет токены в памяти, но не вызывает `session.save()`. Express-session сохранит в конце запроса. В HTTP client flow: после `release()` ожидающий запрос вызывает `session.reload()` из Redis → получает устаревшие данные.

**Решение**: Вызвать `session.save()` после обновления токенов.

### P2: Нет очистки сессии при invalid_grant

**Файл**: `bff/src/services/http-client.ts:109-114`

При `invalid_grant` выбрасывается `UnauthorizedException`, но `accessToken`/`refreshToken` остаются в сессии. Последующие запросы работают с мёртвыми токенами.

**Решение**: Очистить токены из сессии перед抛出ом.

## План исправлений

### Шаг 1: `bff/src/middleware/security.middleware.ts` — убрать expiry check

Убрать блок с `decodeJwt` и проверкой `exp`. Middleware проверяет только:
- `rule.session` → `session?.accessToken` существует
- `rule.csrf` → CSRF валиден
- `rule.roles` → роли sufficient

### Шаг 2: `bff/src/config/routes.ts` — убрать `skipExpiryCheck`

Убрать поле `skipExpiryCheck` из `RouteRule` и из правила `/api/auth/refresh`. Оно больше не нужно.

### Шаг 3: `bff/src/controllers/auth.controller.ts` — lock для refresh

Импортировать `isRefreshing`/`startRefresh`. В `refresh()` добавить lock по `req.session.id`.

### Шаг 4: `bff/src/services/auth.service.ts` — session.save() после рефреша

После обновления токенов вызвать `session.save()`.

### Шаг 5: `bff/src/services/http-client.ts` — очистка при invalid_grant

В блоке `isInvalidGrant`: `session.accessToken = undefined; session.refreshToken = undefined;` перед抛出ом.

### Шаг 6: `client/src/api/api.ts` — рефреш перед logout

В 401-обработчике: вызвать `POST /api/auth/refresh` перед редиректом на logout. Если рефреш успешен — повторить запрос. Если нет — logout.
