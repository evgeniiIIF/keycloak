# Почему AuthGuard падает с 401 на `/api/me`

## Текущее состояние кода

1. **`bff/src/auth/controllers/auth.controller.ts:30-34`** — `@UseGuards(AuthGuard)` на `/api/me` **закомментирован**
2. **`bff/src/app.module.ts:25`** — глобальный `APP_GUARD` **не зарегистрирован** (только `APP_INTERCEPTOR` для `SessionContextInterceptor`)
3. **`bff/src/auth/guards/auth.guard.ts:7-10`** — guard просто вызывает `assertAuthenticated(req.session)` и возвращает `true`

## Что проверяет AuthGuard

`bff/src/shared/utils/assert-authenticated.ts:6-13` — бросает `UnauthorizedException('Session not authenticated')` если **любое** из полей отсутствует:

```
session.accessToken   ← access token от Keycloak
session.refreshToken  ← refresh token
session.idToken       ← id token (OIDC)
session.userInfo?.sub ← subject (ID пользователя)
```

## Сценарии, когда `/me` вернёт 401 (с раскомментированным guard)

### 1. Нет сессии (самый частый)
- Первый визит / инкогнито / очищенные куки
- Express-session создаёт пустой `req.session` без токенов
- `assertAuthenticated` бросает 401
- **Клиент** (`bff/client/src/api/api.ts:26`) ловит 401 → редирект на `/login`

### 2. Сессия есть, но токены не сохранены
- Редкий случай — ошибка в `handleOAuthCallback` (auth.service.ts)
- Код/стейт交换 прошли, но токены не записались в сессию
- Сессия существует (кука есть), но `accessToken` = undefined

### 3. Сессия истекла в Redis
- Кука `connect.sid` ещё жива (browser side), но TTL в Redis прошёл (по умолчанию 86400 сек = 24ч)
- Express-session вернёт пустую сессию → 401

## Почему сейчас guard закомментирован — и это осознанно

`/api/me` — это **endpoint проверки авторизации**. Его вызывает `AuthProvider` (`bff/client/src/context/AuthContext.tsx:23`) при загрузке приложения.

**Сейчас (без guard):**
```
GET /api/me → нет сессии → { user: undefined } → клиент: authenticated=false → рендерит логин
```

**С guard:**
```
GET /api/me → нет сессии → 401 → axios interceptor → редирект на /login
```

Оба варианта работают, но текущий подход **мягче** — приложение рендерится и показывает логин, без принудительного редиректа.

## Вывод

Guard на `/me` **не нужен** по design: этот endpoint — фронт дверь для проверки статуса. Если хочешь защитить `/me`, то потеряешь возможность плавно определить "залогинен/не залогинен" — вместо этого получишь грубый редирект на каждый первый визит.

Если цель — **убедиться, что `userInfo` всегда заполнен** (не просто `undefined`), правильнее сделать это на уровне клиента или вернуть 401 с осознанным сообщением в body, а не через guard (guard = "доступ запрещён", а тут кейс "пока неизвестно").
